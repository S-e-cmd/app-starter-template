# Incident Recovery Protocol

公開中アプリや主要機能が壊れたとき、壊れた状態へ推測修正を重ねず、まず正常稼働へ戻すための手順です。

## 適用条件

次のいずれかが発生した場合、通常の機能追加・整備を中断し、このプロトコルを優先します。

- 白画面、起動不能、ログイン不能。
- 主要機能が使えない。
- 修正後に複数機能が同時に落ちた。
- データが消えた、読めない、初期化されたように見える。
- 公開ページとリポジトリの状態が大きく食い違う。
- 原因不明のまま次の推測修正を重ねようとしている。

## 最優先原則

1. 被害拡大を止める。
2. 最後に正常だったビルド・コミット・公開状態を特定する。
3. 壊れた状態へ修正を重ねない。
4. 原因が明確でない場合は追加上書きよりロールバックを優先する。
5. まず正常稼働へ戻し、その後に別バッチで原因調査と恒久修正を行う。

## ロールバックを優先する条件

次のいずれかに当てはまる場合、原則としてロールバックを第一候補にします。

- 白画面、起動不能、ログイン不能など主要導線が壊れている。
- 修正後に複数機能が同時に落ちた。
- 主要データが消えたように見える。
- 原因がまだ特定できていない。
- 1回の修正で復旧せず、次の推測修正が必要になっている。
- 変更範囲が広く、追加変更の影響を安全に予測できない。

## その場で限定修正してよい条件

次をすべて満たす場合に限り、ロールバックせず限定修正を検討できます。

- 原因箇所が明確。
- 変更範囲が狭い。
- データ互換性に影響しない。
- 修正後の回帰確認が可能。
- 追加修正が新たな推測に依存しない。

## 標準手順

1. 現在の症状、直前変更、公開ビルドを記録する。
2. 最後に正常だったコミット・ビルドを特定する。
3. 保存データ、D1、Sheets、KV、R2、LocalStorage等の状態を確認し、コードだけ戻してよいか判断する。
4. ロールバックまたは限定修正を行う。
5. 起動、主要操作、保存、再読み込み、公開状態を確認する。
6. 正常稼働へ戻った時点で復旧バッチを終了する。
7. 原因調査・恒久修正は別バッチで行う。
8. `docs/PROJECT_STATUS.md` に障害、復旧方法、戻したコミット、未解決原因、再適用可否を記録する。

## 禁止事項

- 原因不明のまま修正を上書きし続ける。
- 壊れた状態を土台に大規模リファクタリングする。
- 復旧と恒久修正を同じバッチに混在させる。
- データ異常時に安易な初期化・削除・再作成を行う。
- ロールバック可能性を確認せず変更を積み重ねる。
- 「画面が開いた」だけで復旧完了扱いにする。

## 復旧完了条件

- 公開ページまたは対象環境が再び起動する。
- 主要機能が動作する。
- 保存・再読み込みが確認できる、または未確認事項が明示されている。
- データ互換性が維持されている、または影響が明示されている。
- 復旧に使用したコミット・ビルドが記録されている。
- 恒久修正が必要な場合は次バッチとして明確に分離されている。
