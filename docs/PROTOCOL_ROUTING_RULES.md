# Protocol Routing Rules

この文書は、複数の開発プロトコルが同時に該当し得る場合の中央判断ルールです。個別プロトコルより先に「今回の主目的」と「高リスク条件」を判定し、別のAIや別Chatでも同じ作業モードを選べる状態にします。

## 1. 主作業モードはユーザーの現在の目的で決める

リポジトリURL、公開URL、`app-starter-template` が提示されていること自体は、整備モードを選ぶ理由にしません。

- 新しいアプリを作る → `CREATE_AND_DEPLOY_FLOW.md` / `BOOTSTRAP_PROTOCOL.md`
- 既存アプリへ機能追加、仕様変更、UI改善、限定的な不具合修正を行う → `FEATURE_CHANGE_PROTOCOL.md`
- 既存アプリ全体の整理、安定化、責務整理、引き継ぎ改善を行う → `EXISTING_APP_ALIGNMENT_PROTOCOL.md`
- 正常稼働していたアプリや主要機能が壊れた → `INCIDENT_RECOVERY_PROTOCOL.md`

ユーザーが明示的に変更を依頼した範囲は変更してよいものとし、それ以外の既存機能、データ、UI、API、公開方式を保護します。

## 2. 高リスク条件は主作業モードへ上書き適用する

通常の更新・整備中でも、次に該当した部分では専用プロトコルを優先します。元の作業目的そのものは失いません。

- 障害・主要機能停止・データ消失疑い → `INCIDENT_RECOVERY_PROTOCOL.md`
- 保存形式、schema、列、API契約等の変更・移行 → `DATA_MIGRATION_PROTOCOL.md`
- Cloudflare、GAS、GitHub連携、Binding、Secret、Variable等の変更 → `ENVIRONMENT_CHANGE_PROTOCOL.md`
- 不要コード、旧API、互換処理、ファイル等の削除 → `CLEANUP_DELETION_PROTOCOL.md`
- ライブラリ、SDK、ランタイム、ビルド基盤等の更新 → `DEPENDENCY_UPDATE_PROTOCOL.md`

例: 「ログイン機能追加」は更新モード。途中でD1 schema変更が必要になった部分だけデータ移行ルールを適用し、移行確認後は更新モードへ戻ります。

## 3. 複数該当時の優先順位

安全性に関わる複数条件が同時に発生した場合は、原則として次の順で優先します。

1. 障害復旧・被害拡大防止
2. データ保全・データ移行
3. 環境・接続設定の復旧または変更
4. 通常の機能追加・仕様変更
5. 非破壊整備
6. 削除・整理

依存更新は状況依存です。

- 依存更新が障害原因または復旧条件 → 障害復旧の一部として扱う。
- 通常のバージョン更新 → 独立した依存更新バッチとして扱う。

削除がmigrationの一部で必要な場合は、migrationの実データ確認完了後にcleanupとして実施します。

## 4. 「既存機能を維持する」の意味

「既存機能を維持する」は、ユーザーが変更を求めた仕様まで固定する意味ではありません。

- ユーザーが明示的に変更を依頼した範囲 → 要望どおり変更対象。
- 依頼範囲外の既存機能、UI、保存データ、API、公開方式 → 維持対象。

依頼範囲の変更に不可避な波及がある場合は、影響範囲を確認して必要最小限に限定します。

## 5. 高リスク・破壊的操作の共通停止条件

次の操作は、ユーザーが明示的に依頼していない限り、根拠、影響範囲、復旧方法を確認せず実行しません。

- 実データの削除・初期化
- D1 table / schema の破壊的変更
- Sheets列・シートの削除
- LocalStorage key の廃止
- API互換の破壊
- Project / Worker / repository の削除
- 公開URLの変更
- Binding / Secret / Variable の削除・改名
- force push、履歴を書き換えるref移動
- 大量ファイル削除・大量rename
- migration確認前の旧互換処理削除

不可逆または復旧困難な操作は、通常の「安全な小変更」と同じ扱いにしません。

## 6. 障害時の last known good

`last known good` は単に直前のcommitを意味しません。

- 主要動作が正常だったことを確認できる最新の commit / build / deployment を指す。
- 正常確認の記録がない場合は「最後に正常だった可能性が高い候補」とし、確定扱いしない。
- GitHub、公開deployment、データschemaの時点が異なる場合は、それぞれを分けて記録する。

## 7. ロールバックの意味

ロールバックは、最後に正常動作が確認されたコード・設定・公開状態へ安全に戻すことを指します。

原則としてGit履歴を書き換えない方法を優先します。

優先例:

- 問題commitを `revert` する。
- 過去正常版の内容を復元し、新しいcommitとして反映する。
- Cloudflare等のdeploymentを最後の正常版へ戻す。

原則避けるもの:

- `reset --hard` を前提とした履歴巻き戻し。
- force push。
- 問題変更と無関係な正常変更までまとめて消す上書き。

公開deploymentだけを戻した場合は、GitHubとの不一致を一時状態として `PROJECT_STATUS.md` に記録し、放置しません。

## 8. 「1回の限定修正」の定義

障害時の「1回の限定修正」は、次の1サイクルを指します。

1. 原因仮説を1つに絞る。
2. 小規模な変更を行う。
3. 対象環境へ反映する。
4. 復旧確認を行う。

コードを書いただけ、commitしただけ、未反映の変更は「1回」に数えません。

原因不明のまま、このサイクルを繰り返して上書きし続けません。

## 9. 検証結果の状態表現

作業結果は次の3状態に統一します。

- **完了** — 実装・変更と必要な検証が完了している。
- **作業完了 / 検証保留** — 変更自体は完了したが、外部環境、権限、公開取得不可等により必要な検証の一部が残る。
- **未完了** — 実装、復旧、移行、設定変更そのものに未処理が残る。

未確認を成功扱いにも失敗扱いにもせず、何が未確認かを明記します。

## 10. 検証中に別問題を発見した場合

- 今回の変更が原因 → 原則として同じバッチで修正・再確認する。
- 今回の変更と無関係な既存問題 → `PROJECT_STATUS.md` に記録し、別バッチへ回す。
- 重大障害、データ損失、セキュリティ問題 → 通常バッチを中断し、該当する高リスクルールへ切り替える。

「見つけたからついでに直す」で作業範囲を無制限に広げません。

## 11. 再利用の判断

既存部品・共通処理は、次を満たす場合に優先して再利用します。

- 責務が一致している。
- 不要なアプリ間依存を増やさない。
- データ契約や公開方式を不自然に結合しない。
- 再利用のための互換層が新規実装より複雑にならない。

再利用そのものを目的にしません。

## 12. 同時編集・競合時

書き込み前に取得したSHAや内容が古くなっていた場合、古い内容で上書きしません。

1. 最新版を再取得する。
2. 他者または別Chatの変更を確認する。
3. 自分の変更だけを最新内容へ再適用する。
4. 競合解消のために他の正常変更を無断で削除しない。

409等の競合は「上書きしてよい」という意味ではなく、再取得して差分を統合する合図として扱います。

## 13. セキュリティ事故

Secret、APIキー、認証情報、非公開データの漏えいが疑われる場合は通常障害より先に被害拡大防止を行います。

- 漏えいしたSecret / tokenの失効・ローテーションを優先する。
- 公開範囲やアクセス経路を必要に応じて遮断する。
- 値そのものをログ、issue、commit、チャットへ再掲しない。
- 復旧後にコード・履歴・設定への残存を確認する。

## 14. 完了判定の共通原則

コードを書いた、commitした、deployが開始された、というだけでは完了ではありません。

作業目的に応じて、必要な範囲の以下を確認します。

- 対象機能
- 隣接する既存機能
- 保存・再読み込み
- API / 外部連携
- データ互換性
- PC / スマートフォン表示
- 公開反映・ビルド番号
- 必要なドキュメント更新

確認不能な項目がある場合は `作業完了 / 検証保留` とし、未確認項目と再開地点を残します。
