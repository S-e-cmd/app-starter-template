# Feature Change Protocol

立ち上げ後の通常の機能追加・仕様変更・小規模改修を、安全に継続するための標準手順です。

## 適用範囲

次のような依頼では、この手順を使用します。

- 新機能追加
- 既存機能の拡張
- UI追加・操作改善
- 保存処理やAPI連携の追加
- 小規模な仕様変更
- 不具合修正に伴う限定的な関連整理

新規アプリの初期作成は `BOOTSTRAP_PROTOCOL.md`、既存アプリ全体の非破壊整備は `EXISTING_APP_ALIGNMENT_PROTOCOL.md` を優先します。

## 基本原則

- 既存機能を維持する。
- 変更対象と影響範囲を先に確認する。
- 既存の責務、データ契約、UIルール、公開方式を尊重する。
- 同等機能や再利用可能な既存部品がある場合は、重複実装を避ける。
- 新しい責務を既存の巨大ファイルへ安易に追記しない。
- 機能追加のついでに無関係な大規模整理を行わない。
- 保存形式、API、既存ID、LocalStorageキー、D1 schema、Sheets列等の互換性を優先する。
- 必要な整理は、今回の変更に直接関係する範囲だけで行う。

## 変更前

1. ユーザー要望と完了条件を確認する。
2. 対象機能の現在実装と関連ファイルを確認する。
3. 呼び出し元・呼び出し先・共有状態を確認する。
4. 既存の共通部品、類似機能、再利用候補を確認する。
5. 保存先、API、外部サービス、公開方式への影響を確認する。
6. PC / スマートフォン双方のUI影響を確認する。
7. `ai-context.json` と関連する `docs/` を確認し、保護対象と既知問題を把握する。

変更対象と隣接範囲が把握できたら、無関係な全体再確認は行いません。

## 実装方針

- 既存責務の延長なら既存モジュールを使用する。
- 新しい責務なら、その責務に合うモジュールやファイルを追加する。
- 巨大ファイルへ追加する必要がある場合は、今回触る責務だけを安全に分離できるか検討する。
- 分離する場合も、今回の機能追加と回帰確認が同時に完結できる小さな境界に限定する。
- イベントハンドラへ通信、保存、変換、業務ロジックを直接埋め込まない。
- 新しいUIは既存の表示ルール、操作感、レスポンシブ方針を優先する。
- 待ち時間のある操作には処理中表示と二重操作防止を入れる。
- エラーは握り潰さず、利用者向け表示と確認用ログを分ける。
- 既存データを読めなくする変更は行わない。必要な場合は互換処理またはmigrationを用意する。
- Secret、Variable、Binding、公開URL、デプロイ方式は、明確な理由なく変更しない。

## やってはいけないこと

- 機能追加を理由にアプリ全体を書き直す。
- テンプレートに合わせるためだけに既存構成を変更する。
- 行数削減だけを目的に大量分割する。
- 不具合修正と無関係な大規模リファクタリングを同じ変更に混ぜる。
- 既存保存形式やAPIを、互換策なしで置き換える。
- 動作確認前に古い処理を削除する。
- ユーザー依頼外のUI・仕様を大きく変更する。

## 変更後の必須確認

今回の変更範囲と関連する既存機能について、可能な範囲で次を確認します。

1. 構文・JSON・設定形式が正常。
2. 初期表示が正常。
3. 追加・変更した機能が正常。
4. その機能に隣接する既存操作が正常。
5. 保存・再読み込みが正常。
6. 関連API・外部連携が正常。
7. エラー時・処理中表示が適切。
8. PC / スマートフォン双方で重大な表示崩れがない。
9. 既存データ契約が維持されている、またはmigrationが確認できる。
10. 公開が伴う場合は、公開画面とリポジトリのビルド番号が一致している。

全アプリを毎回最初から確認するのではなく、今回の影響範囲に応じて回帰確認を限定します。

## ドキュメント更新

コード変更と同じ変更単位で、必要なものだけ更新します。

- 構成・責務・依存関係が変わった → `docs/ARCHITECTURE.md`
- API・保存形式・schema・列構成等が変わった → `docs/DATA_CONTRACT.md`
- UI上の維持事項・操作ルールが変わった → `docs/UI_RULES.md`
- 安定機能、開発中項目、既知問題、次タスクが変わった → `docs/PROJECT_STATUS.md`
- エントリーポイントや主要構成が変わった → `ai-context.json`

コードだけ更新し、現在状態を示す情報が古いままなら完了扱いにしません。

## 完了条件

次を満たしたとき、その機能追加・改修を完了扱いにします。

- 依頼された機能・修正が実装されている。
- 既存の関連機能が維持されている。
- データ互換性が維持されている、または必要な移行が成立している。
- 変更影響範囲の回帰確認が完了している。
- 必要なドキュメントが現在状態へ更新されている。
- 公開を伴う場合は、公開反映とビルド番号を確認している。

機能追加時の目的は、単に新しい処理を足すことではなく、次の変更でも安全に触れる状態を維持することです。
