# Existing App Alignment Protocol

既存アプリを壊さず、今後の修正・引き継ぎを安全にするための非破壊整備手順です。

## 適用条件

まず `docs/PROTOCOL_ROUTING_RULES.md` で主作業モードを判定します。

このモードは、ユーザーの現在の目的が次に該当する場合に使用します。

- 既存アプリ全体の整理・安定化
- 責務混在や巨大化の段階的な改善
- 引き継ぎ情報の整備
- 今後の変更を安全にするための保守性改善
- 特定の新機能ではなく、既存アプリ全体の状態確認と整備

既存アプリのGitHubリポジトリ、公開ページ、`app-starter-template` が提示されていること自体は、このモードを選ぶ理由にしません。具体的な機能追加・仕様変更が主目的なら `FEATURE_CHANGE_PROTOCOL.md` を使用します。

このモードでは、テンプレート準拠そのものを目的にしません。テンプレートは判断基準・保守ルールとしてのみ使用します。

## 最優先原則

### 1. 壊さない

- ユーザーが明示的に変更を依頼した範囲は変更対象として扱う。
- 依頼範囲外の既存機能、既存UI、保存データ、API契約、公開方式、公開URLを保護対象として扱う。
- 公開中の正常動作と既存データ互換性をテンプレート構成より優先する。
- 大規模変更、一括置換、根拠のない削除、テンプレートに合わせるだけの再構成を行わない。
- 変更前に影響範囲を確認し、変更後に回帰確認する。

### 2. 「できない」で止めない

- 権限、ツール、外部サービス等の制約があっても、そこで作業を終了しない。
- 現在可能な確認、修正、切り分け、代替手段、準備作業を先に進める。
- ユーザー操作が本当に必要な箇所だけ、対象・場所・入力値・次の確認事項を具体的に提示する。
- 未確認を「できない」「異常」と同義に扱わない。

### 3. できる量ごとに進める

- 一度に全体を作り直さない。
- 安全な小単位で `確認 → 修正 → 回帰確認 → 記録` を完結させてから次へ進む。
- 1バッチで触る責務・機能・ファイル群を限定する。
- 変更量が大きくなる場合は途中で区切り、未完了項目を記録して継続する。

## 高リスク条件への切替

整備中に障害、データ移行、環境設定変更、削除、依存更新が必要になった場合は `PROTOCOL_ROUTING_RULES.md` に従い、該当部分だけ専用プロトコルを優先します。整備目的そのものは失いません。

## テンプレートの扱い

既存アプリでは次を禁止します。

- テンプレート準拠率を上げることを目的にする。
- 既存構成を `core` / `cloudflare-worker` / `d1` / `sheets-gas` の構成へ無理に変換する。
- ファイル名、ディレクトリ構成、公開方式をテンプレートに合わせるだけの変更を行う。
- テンプレートとの差分そのものを修正理由にする。
- 正常稼働している既存方式を、テンプレートの既定方式へ置き換える。

テンプレートから取り入れるのは、非破壊で有益な保守ルール、引き継ぎ情報、責務分離の考え方、データ互換性ルール、確認手順です。

## 最初に確認すること

変更前に、可能な範囲で次を確認します。

- 公開ページの実際の表示・主要動作
- リポジトリ構成と現在ビルド
- 主要機能と既知の問題
- APIの入口・レスポンス形式
- LocalStorage / D1 / Sheets / KV / R2 等の保存先
- 既存データ形式、キー、ID、schema、列構成
- Cloudflare Workers / Pages 等の公開方式
- Git連携、自動デプロイ方式、Production branch
- Binding、Secret、Variable、既存プロジェクト名
- `ai-context.json` / `llms.txt` / `docs/*` の有無と鮮度

公開ページとリポジトリの状態が食い違う場合は、公開中の実挙動を重要な事実として扱い、原因を確認するまでコードだけを正として壊さないようにします。

## 整備の優先順位

1. 現状確認と保護対象の明確化。
2. 不足している自己引き継ぎ情報を追加・更新する。
3. 現在の構成、データ契約、UI制約、現在状態を文書化する。
4. 明らかな責務混在のうち、影響範囲が確認できる箇所だけ安全に整理する。
5. 今後の機能追加で触る範囲から段階的に分割する。
6. 不要コード削除は最後に行い、動的参照・外部連携・互換処理まで確認する。

## 保護対象

既存の次の要素は、明確な理由と互換性確認なしに変更しません。

- LocalStorageキー
- D1 schema / migration履歴
- Sheetsの列構成・シート名
- JSON形式・API契約
- 既存ID・識別子
- Worker / Pages構成
- Binding名
- Secret / Variable名
- Git連携・デプロイ方式
- 公開URL
- 依頼範囲外の主要UIフロー

変更が必要な場合は、互換性維持策、migration、段階移行、ロールバック可能性を先に確認します。

## 1バッチの標準手順

1. 今回扱う範囲を限定する。
2. 対象と関連箇所を確認する。
3. 保護対象と影響範囲を確認する。
4. 必要最小限の変更を行う。
5. 構文、初期表示、主要操作、保存、再読み込み、関連API、公開状態を可能な範囲で確認する。
6. `docs/PROJECT_STATUS.md` に今回の変更、確認済み範囲、未確認範囲、残タスク、意図的な例外を記録する。
7. 現在の整備必要度を評価し、次の推奨と選択肢を提示する。
8. ユーザーが継続を選んだ場合だけ、次の安全なバッチへ進む。

不具合修正と大規模リファクタリングは同じバッチへ混在させません。

検証中に別問題を見つけた場合、今回の変更が原因なら同じバッチで扱い、無関係な既存問題は `PROJECT_STATUS.md` に記録して別バッチへ回します。重大障害・データ損失・セキュリティ問題は専用高リスクプロトコルへ切り替えます。

## 整備必要度の評価

各バッチ終了時に、テンプレートとの差ではなく現在の壊れやすさと未確認リスクを基準に、次の4段階で評価します。

### 高 — 続行推奨

- データ消失や互換性破壊につながる構造がある。
- 公開障害や主要機能停止につながる不安定要因がある。
- 変更影響範囲が極端に広く、今後の小さな修正でも事故が起きやすい。
- 重要な保存処理・API・外部連携が未把握または危険な責務混在状態にある。

### 中 — もう少し整備推奨

- 現在は正常に動いているが、大きな責務混在が残っている。
- 次回の機能追加や不具合修正で影響範囲が広がりやすい。
- 引き継ぎ情報が部分的に不足している。
- 継続保守上の明確な改善余地がある。

### 低 — 今回で終了して問題なし

- 既存機能とデータ互換性が保護されている。
- 現在構成・主要データ契約・公開方式が把握されている。
- 次の作業者が安全に続けられる引き継ぎ情報がある。
- 残りが主に改善・美化・任意リファクタリングである。

### 保留 — 判断材料不足

公開ページ、外部サービス、保存先、主要API等の重要箇所が未確認で、安全性を評価できない場合です。

未確認を異常扱いせず、何が確認できていないため保留なのかを明記します。

## 評価基準

整備必要度は次を材料に判断します。

- データ消失・互換性破壊の可能性
- 公開障害・主要機能停止の可能性
- 次回変更時の影響範囲
- 責務混在による修正事故の可能性
- 重要な外部連携・保存先の未確認度
- 引き継ぎ困難度

テンプレートとの差、ファイル名、ディレクトリ構成、テンプレート準拠率は危険度判定の材料にしません。

## 各バッチ終了時の必須報告

`docs/BATCH_COMPLETION_CHOICES.md` に従い、整備必要度、理由、推奨、説明付きの選択肢を提示します。

- `[続ける]` — 次の具体的な安全バッチを併記する。
- `[今回は終了]` — 現在状態と再開地点を記録して終了する。
- `[別の箇所を優先]` — ユーザーが機能・UI・保存・公開周り等を指定できることを説明する。

## 自己引き継ぎ情報

既存アプリに不足している場合は、作り直さず現状に合わせて次を追加します。

- `ai-context.json`
- `llms.txt`
- `docs/ARCHITECTURE.md`
- `docs/DATA_CONTRACT.md`
- `docs/UI_RULES.md`
- `docs/PROJECT_STATUS.md`

これらはテンプレートの理想構成を書くのではなく、現在のアプリの実態を書くためのものです。

既存アプリに `ai-context.json` がないことだけを理由に、新規アプリとして再ブートストラップしません。

## 完了判定

`PROTOCOL_ROUTING_RULES.md` の状態表現を使用します。

- **完了** — 必要な整備と検証が完了。
- **作業完了 / 検証保留** — 整備変更は完了したが、外部環境等の理由で必要検証の一部が残る。
- **未完了** — 整備そのものに残作業がある。

既存アプリでは「テンプレートに寄せる」ことではなく、「今の構成を尊重しながら、壊れにくく、引き継ぎやすくする」ことを最上位目的とします。
