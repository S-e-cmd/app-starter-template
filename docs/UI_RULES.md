# UI Rules

## 既存UIの保護

- ユーザーが直接変更を求めた範囲以外の既存画面構成・主要導線・情報量を変更しない。
- 新機能追加のために既存要素を縮小・削除しない。
- 見栄えの改善を、情報量・一覧性・操作数・既存配置・主要導線を悪化させる理由にしない。
- 一覧性を目的とする画面では、詳細機能追加によって一覧性を落とさない。
- 「モダンに」「見やすく」「余白を増やす」等の一般論だけを根拠に情報密度を下げない。

## PC / SP

- PC/SPの双方で操作可能な状態を維持する。
- PCレイアウトの単純縮小をスマホ最適化とみなさない。
- スマホ対応のためにPC版を悪化させない。
- 画面幅だけを理由に主要機能を削除しない。
- PC/SPそれぞれで既存の利用目的・情報量・主要操作を維持する。

## 共通UI

- ボタン、入力欄、モーダル、トースト、処理中表示は、責務と操作目的が一致し不要な結合を増やさない場合に既存共通実装を優先する。
- 待ち時間のある操作は処理内容を表示し、二重操作を防止する。
- 成功、失敗、未実行、再試行待ちを区別する。
- 新しい色・card・modal等は、直接要望または具体的な機能上の必要性がない限り追加しない。

## UI回帰確認

変更対象に応じて次を `verified / blocked / not-applicable` で確認します。

- 主要ボタン・リンクの押下可能領域。
- scroll / nested scroll。
- overflow / 横はみ出し。
- modal open / close / backdrop。
- focus / keyboard操作。
- pinch / drag / swipe等のgesture。
- fixed / sticky要素。
- z-index / overlay重なり。
- PC/SPでの情報欠落。
- 一覧性・列数・カード密度。
- loading / success / error状態。

blockedなら理由、代替確認、残存リスクを記録します。

UI上の維持事項や例外が増えた場合は、各アプリの `docs/UI_RULES.md` に記録します。
